# 0.1.27 同步性能与进度改进

本轮围绕 WebDAV 慢、容易中断，以及同步范围不可见的问题实施。四种服务共用预扫描和任务进度；其他网盘同时改进桌面端连接复用和传输超时。

## 同步流程

1. 扫描网盘和本地，显示已发现的文件、文件夹数量。此时还不知道总量，不显示虚假的百分比。
2. 生成完整同步计划：上传、下载、删除、创建文件夹、冲突及预计传输量。正常流程自动开始；已有的大规模变更保护继续生效。
3. 执行计划，显示当前文件和“已确认完成 / 总任务”。失败任务不会推动完成进度，终止后区分成功、失败和未执行。
4. 历史记录保留统计、文件目录与可展开的诊断摘要。诊断摘要仅含耗时、数量、阶段及 WebDAV 请求统计，不包含文件路径、账号或令牌。

预计传输量不是实时网络流量；加密、冲突处理和未知大小文件可能造成差异。

## 已实施的优化与保护

- 密码检查复用完整网盘扫描结果，避免正常同步为检查密码额外扫描一次。大规模变更确认后仍需重新检查，避免按过期计划执行。
- WebDAV 目录使用并发队列滚动调度，避免每批目录必须等待最慢请求。收到限流响应后降低扫描并发。
- 列表、读取和状态检查对部分临时错误最多尝试三次，使用退避并有限尊重 Retry-After。认证失败和写操作不会盲目重试；扫描失败不会当作空目录继续同步。
- 有强 ETag 时复用扫描元数据，并使用条件请求保护传输。上传响应丢失时尝试核实远端版本和内容，确认一致才记成功，不直接重复上传。
- 下载前后检查本地计划状态；删除文件夹前检查是否出现新文件；确认后的版本复核包含 ETag。检测到变化时停止相关操作，重新同步生成计划。
- 按预计文件大小限制同时传输的缓冲占用，默认预算 64 MiB，超大单文件独占预算。这不是整个进程的内存上限，加密及传输库仍会分配额外内存。
- 百度、夸克、阿里桌面传输复用 HTTPS 连接，根据数据大小设置总超时，并保留空闲超时、TLS 和传输地址校验。
- 运行中的界面刷新合并到约 200 毫秒一次，减少频繁更新。

## 本地性能探针

执行 `node docs/diagnostics/webdav-performance-probe.cjs` 可复现模拟结果。目录滚动调度避免慢目录阻塞后续目录，临时 503 可恢复。模拟耗时不能代表真实网盘提速比例。

100 个小文件上传仍保留 100 次上传及 100 次上传后状态确认。没有通过删除完整性检查来换取表面速度。

## 仍有边界

- WebDAV 服务端能力不同；没有强 ETag 的服务只能采取更保守的检查，无法提供与原子条件请求完全相同的保障。
- 通用 WebDAV 不具备统一的断点续传接口。本轮未实现跨次运行的持久化断点恢复。
- 其他网盘内部的写入队列及必要内容校验保留，后续应根据真实诊断数据分别优化。
- 本地自动化测试不能替代用户真实网盘验证；本轮没有访问用户网盘或测量真实提速比例。

## 安装与分步实测

先备份笔记库及现有插件文件，将安装包中的 main.js、manifest.json、styles.css 覆盖到 `.obsidian/plugins/remotely-save-next/`，完全退出并重新打开 Obsidian，确认版本为 0.1.27。保留原 data.json，避免丢失登录设置。

1. 首先使用独立的 WebDAV 测试目录，放入若干笔记和附件。运行同步，观察“扫描 → 计划 → 执行”的顺序以及当前文件。
2. 再同步一次：没有变化时应显示没有待处理任务。
3. 修改一个文件、新增一个文件，核对计划和历史统计；文件夹也计入任务，因此任务总数不一定等于文件数。
4. 检查实际内容后，再用原笔记库测试。如果中途失败，提供历史记录中的诊断摘要和错误提示，便于区分扫描、下载、上传和限流问题。不要提供 Cookie、令牌或完整授权链接。
5. WebDAV 验证后，再分别验证百度、夸克、阿里。不要同时更换多种服务，以免难以定位问题。

## 本轮验证结果

- TypeScript 类型检查通过。
- 完整基线：552 项主测试、110 项 WebDAV 测试通过，无失败。
- WebDAV 诊断探针 11 项通过；性能探针验证滚动调度、临时错误恢复及必要上传确认次数。
- 独立代码复核发现的文件夹删除保护和版本标识遗漏已修复，并加入回归用例。
