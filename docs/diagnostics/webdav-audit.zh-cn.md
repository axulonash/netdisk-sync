# WebDAV 自主排查与分阶段实施细则草案

日期：2026-10-03。基线：本地 HEAD `34db181`，插件 0.5.25。

后续进展见 [阶段一构建与 HTTP 复现基线](stage-1-baseline.zh-cn.md)。下文保留第一轮排查时的验证范围。

## 范围与证据等级

本轮仅排查和规划，未修改生产代码，未连接用户网盘。

- 静态追踪：WebDAV 适配、加密包装、同步计划和实际删除链路。
- 本地诊断：直接读取当前 TypeScript 源码，使用 Node 自带类型擦除功能，在隔离环境注入模拟客户端。没有复制改写待测方法。
- 依赖核查：下载并只读检查 npm 官方分发的 `webdav@5.6.0` 包。项目依赖声明为 `^5.6.0`，未发现锁文件，因此这不代表用户实际安装包的精确版本。
- 当前工作区没有 node_modules；没有运行完整项目构建和原有测试，也没有执行 HTTP 服务端、Obsidian 桌面或移动端集成测试。
- 脚本中的基础队列、分片辅助函数、SDK 和持久化均为替身；它验证适配层控制流，不验证第三方库、真实服务端和数据库行为。

复现命令（Node >= 22.13，当前实测 Node 26.10.0）：

```sh
node docs/diagnostics/webdav-audit.cjs
```

11 项探针均确认预期的现有行为。这里的“确认”包含缺陷复现与正常行为对照，不表示插件修复或集成测试通过。

## 已复现及静态确认的问题

### W01：远端删除失败被吞掉（优先级 P0）

- 位置：`src/fsWebdav.ts:912`，`pro/src/sync.ts:1570`。
- 模拟 SDK 删除抛出 HTTP 403，`rm()` 仍正常返回。
- 上层删除分支在 `await fsEncrypt.rm()` 后清除同步历史。静态链路表明，删除未成功也可能继续清除历史；本轮未运行数据库集成测试。
- 影响：同步状态失真，后续可能把仍存在的远端文件作为新文件处理。
- 实施：传播删除失败；单独定义已不存在文件的幂等语义；确认成功后才能清理历史。不能把所有 4xx 都视为成功。
- 验收：403、429、5xx、断网不清除历史；成功删除可清除；404 行为有独立用例。

### W02：Apache/Sabre 分块写入先清空正式目标（P0）

- 位置：`src/fsWebdav.ts:804`、`:842`。
- Apache 分支模拟旧文件 100 字节、第一次部分写入断网，正式目标已经成为 0 字节。Sabre 分支通过静态检查确认同样先写空文件。补充：实际 SDK 的 Apache 部分写入使用范围 PUT，Sabre 使用 PATCH；第一轮仅在 SDK 方法边界模拟错误。
- 影响：即便同步最终报错，旧远端副本也已被破坏，重试不能恢复旧内容。
- 实施：优先停用不具备安全提交保障的特殊分块路径；评估临时对象写入、校验、MOVE 提交。MOVE 的覆盖和原子性要按服务端验证，不能默认所有 WebDAV 都具备。
- 验收：在每个分块和提交步骤注入中断；旧目标保持完整，或提供已验证可恢复的副本；失败不记录成功。

### W03：初始化状态以 client 是否存在代替初始化完成（P1）

- 位置：`src/fsWebdav.ts:287`。
- 第一次根目录检查抛错后，第二次 `_init()` 不重试检查，直接返回。
- 第一个 `_init()` 尚未结束时，第二个调用者可以提前返回。
- 适用边界：同一适配实例；`main.ts` 每次同步会创建新实例，不能据此断言故障跨所有同步任务永久持续。
- 实施：共享初始化 Promise；失败清理状态，允许重试；所有调用等待初始化完成。
- 验收：并发初始化只执行一次完整流程；第一次失败后能恢复；不发出早于初始化完成的业务请求。

### W04：可选分块能力探测失败阻断普通同步（P1）

- 位置：`src/fsWebdav.ts:380`。
- 根目录存在，但 `getDAVCompliance()` 抛出 OPTIONS 405 时初始化失败。
- SDK 5.6.0 会对 OPTIONS 错误状态抛异常，适配层没有区分“不支持能力探测”和“连接本身失败”。
- 实施：对已确认的能力不支持响应降级到普通上传；认证失败、网络异常等需分别处理，不做全量吞错。
- 验收：OPTIONS 405/501 且基本操作可用时可以同步；401/403 等仍给出明确诊断。

### W05：Nextcloud 分块上传的名称、URL 和配置不一致（P1）

- 位置：`src/fsWebdav.ts:697`。
- `/vault/a/同名#附件.bin` 和 `/vault/b/同名#附件.bin` 生成相同临时目录名。并发、多设备或失败重试可能冲突；本轮验证名称碰撞，未模拟服务器端内容混合。
- `Destination` 直接拼接会产生 `/user//vault/`；`encodeURI()` 保留 `#`，标准 URL 解析将后面的部分视为 fragment，而不是文件名。双斜杠是否被容忍取决于服务端。
- 分块子客户端只带固定 Cache-Control，没有继承用户自定义请求头。
- 临时名称又被 SDK 编码，导致已经百分号编码的中文进一步编码；单纯二次编码不一定使上传失败，但会扩张临时名称。
- 官方 Nextcloud 分块协议要求创建唯一上传目录，建议随机 UUID。
- 实施：独立的短随机上传 ID；统一构造 Destination；复用连接配置；失败清理上传会话；验证最终内容和大小。
- 验收：两个目录同名文件并发上传、两实例并发、失败重试、中文/空格/#/%、自定义认证头均覆盖。

### W06：Nextcloud 地址末尾斜杠改变能力检测结果（P2）

- 位置：`src/fsWebdav.ts:380`。
- 相同 endpoint，无尾斜杠被识别为 Nextcloud，有尾斜杠不被识别；上传地址辅助函数虽会去掉尾斜杠，但前面的检测分支不会。
- 实施：检测与上传地址推导复用规范化后的 URL。
- 验收：有无尾斜杠行为相同；不能破坏包含编码路径段的用户名。

### W07：OpenSSL 将整条路径编码成单个长文件名（P1，兼容性设计项）

- 位置：`src/fsEncrypt.ts:493`、`src/encryptOpenSSL.ts`。
- 用实际加密函数验证：6 段各 30 个英文字符的目录加 `/note.md`，原始路径 193 字节，每段最多 30 字符，输出单个 299 字节名称。
- 因此“本地目录不深、单个名称不长”不代表加密后的远端单文件名短。
- 255 字节仅作为说明这一机制的示例限制，不是对所有 WebDAV 服务的统一阈值。
- 尚不能断言这是用户实际故障原因：不知道其加密模式和服务端限制。rclone 模式需另行验证，不能套用 OpenSSL 的结论。
- 实施：在加密后、发送前分析实际远端名称；区分字符数、UTF-8 字节数和 URL 编码后长度。先报告可解释错误，不自动改名、截断、切换加密或迁移数据。
- 若确认服务端硬限制：另立“短名称对象存储”设计，明确远端格式版本、路径映射、多设备冲突、恢复、迁移和回滚，完成设计后单独实施。
- 验收：加密/不加密、中文/英文/Emoji、长单段/深目录分别验证；支持阈值从服务配置或实测得出。

## 待实机或传输层验证

- `tryEncodeURI()`（`src/fsWebdav.ts:216`）遇到任意 `%` 就原样返回。包含 `%20` 和未编码中文/空格的混合地址确实不会被规范化，但 Obsidian 请求层可能再编码；目前仅确认函数行为，不能直接认定连接失败。
- 服务端 URI、路径、单文件名和反向代理请求限制，需要分别注入 414、403、409 等响应。状态码不是长度问题的唯一判据。
- iOS 专用 401 重试、Digest 认证、代理、自签名证书、限流和超时尚未实机验证。
- 服务端成功返回但漏列文件，无法仅靠 HTTP 成功码识别；需要服务特征、扫描完整性证据和删除保护共同设计，不能承诺通用“自动判断列表完整”。

## 已排除的过度判断

- 普通 PUT 路径以原始名称交给 SDK，SDK 5.6.0 的 encodePath 负责百分号编码，不能据 Nextcloud 手工拼 URL 的问题推断普通 PUT 都错误。
- `walk()` 中目录请求抛错会向上传播；同步引擎等待远端扫描完成后才生成计划。不是“任何扫描失败都会使用半份列表”。
- SDK 默认排除目录自身，当前证据不支持把递归扫描无限循环列为已确认缺陷。
- 自定义 MOVE/PATCH 在 SDK 5.6.0 会检查响应状态，不应误报为“customRequest 从不检查 HTTP 错误”。

## 建议按步骤制定并执行的实施细则

本节是草案，不代表已经实施。各阶段完成后保留可运行版本，禁止在一次大改中同时改变远端格式、服务后端和同步算法。

### 阶段一：WebDAV 稳定性基线与诊断

1. 安装和记录确定的依赖版本，建立可重复构建，运行原有测试；单列基线已有失败。
2. 搭建可控制响应的本地 HTTP/WebDAV 服务，使用独立临时仓库，禁止复用真实笔记目录。
3. 将本轮缺陷探针转为正式回归用例：修复前失败，修复后通过。本轮脚本用于观察旧行为，不能直接当“应当保持”的回归断言。
4. 建立最小诊断结构：操作、阶段、状态码、耗时、重试次数、路径匿名标识、各类长度。默认不记录凭据、Authorization、Cookie、笔记正文、带口令的完整 URL。
5. 覆盖全量扫描、CRUD、MOVE、中文特殊字符、0 字节文件、10 MiB 分支边界、目录数量、加密和网络中断。

交付：构建基线、正式测试夹具、脱敏错误样例与失败分类；此时才宣称具备 HTTP 层复现能力。

### 阶段二：优先修复 WebDAV

1. 先处理 W01/W02，保护同步历史和旧远端副本。
2. 再处理 W03/W04，建立可靠初始化与能力降级规则。
3. 处理 W05/W06，并对普通上传和 Nextcloud 特殊路径分别回归。
4. 加入 W07 长度诊断，保留现有远端布局；短名称存储另立版本，不混入兼容修复。
5. 补充重试分类：可重试错误、有上限退避、幂等操作与非幂等操作分别处理。分块 append 不能盲目重试，否则可能重复追加。

交付：每个问题的复现、修复、回归证据；桌面和移动端验证结果明确分开。

### 阶段三：界面与后端精简

1. 设置拆为连接、同步、状态三块；高级选项折叠，调试工具独立。
2. 按后端注册表组织配置和客户端创建，删除无关后端及其专属依赖。
3. 清理 pro 登录/推广界面前追踪依赖；同步入口仍在 pro/src/sync.ts，不能直接删目录。
4. 旧配置备份与版本化迁移；被移除服务进入待配置状态；不自动换网盘同步。
5. 百度/夸克适配未通过验收前不显示为“可用”。

交付：页面对照、旧 WebDAV 配置迁移用例、构建产物及依赖变化。

### 阶段四：百度、夸克新增适配

1. 分别先核实官方接口准入和 Obsidian 桌面/移动运行条件。
2. 验证授权刷新、完整分页、上传覆盖、下载、空文件、删除、重命名及限流。
3. 实现统一 FakeFs 合同；时间戳精度和内容变更识别必须实测，不直接照搬其他服务。
4. 两端设备运行新增、修改、删除、冲突和中断恢复测试。
5. 原生路线受限时，再决定是否接受额外 WebDAV 中间服务；界面明确接入方式。

交付：每个网盘独立的能力清单、限制说明和双端验收结果。

### 阶段五：独立分支迁移与发布准备

1. 明确插件 ID、名称、配置和本地数据库命名，避免原版与修改版相互干扰。
2. 迁移前后比较同步计划；首次执行检查异常批量变动。
3. 若引入新远端格式，旧客户端不得继续写入同一远端；提供迁移和恢复流程。
4. 保留来源及许可证信息，整理安装和回滚说明。
