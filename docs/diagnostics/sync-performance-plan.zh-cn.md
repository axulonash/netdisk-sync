# 同步性能排查与优化方案

日期：2026-10-10；代码版本：0.1.26。用户反馈主要来自 WebDAV。

本轮只分析、运行隔离探针并编制方案，没有修改同步行为。尚未获取用户实际服务类型、文件规模和失败原始日志，因此以下区分已确认的代码问题与尚待验证的现场原因。

## WebDAV 已确认的问题

| 问题 | 代码证据 | 影响 |
| --- | --- | --- |
| 每次同步完整扫描远端 | `pro/src/sync.ts` 的远端 walk；`src/fsWebdav.ts` 的 walk | 即使只改一个文件，也先逐目录列举；目录多、层级深时开始传输前等待较长。完整扫描本身有保障多端一致性的作用，不能直接删掉。 |
| 扫描存在批次和层级屏障 | walk 每批固定 10 个请求，Promise.all 等整批结束，再进入下一批；本层全部结束才遍历下一层 | 单个慢目录拖住后续任务，且扫描并发与文件传输并发分离，没有针对服务端限流自适应。 |
| 普通上传需要两个远端操作 | `_writeFileFromRootFull` PUT 后调用 `_statFromRoot` | 小文件速度受请求往返影响；不能把网盘标称带宽当成小文件同步速度。属性确认有用途，应优化而非直接删除。 |
| 下载前重复查询属性 | `src/copyLogic.ts` copyFile 先 stat 再 readFile | WebDAV 下载通常是 PROPFIND 加 GET，扫描取得的信息未被复用；复用需要保留版本变化检测。 |
| 瞬时扫描失败不重试 | WebDAV request patch 直接 requestUrl；walk 无重试 | 一次临时服务错误即可使整轮扫描失败。SDK Digest 鉴权和 iOS 特殊 401 回退不是通用网络重试。 |
| 单个执行错误阻断后续阶段 | `pro/src/sync.ts` doActualSync 的 potentialErrors 分支 | 同层队列结束后，只要有错误就抛出；累计三个错误还会清空待执行任务。成功文件已有各自同步记录，并非所有进度丢失，但重新同步仍会重新扫描。 |
| 传输控制和诊断不足 | WebDAV patch 仅向 requestUrl 转发 URL、方法、正文和请求头等字段 | 插件没有清晰的单请求超时、取消和重试预算；不能据此断言 WebDAV 使用了其他适配器的 60 秒超时，也不能把 UI 超时等同于底层请求已取消。 |
| 通用 WebDAV 大文件没有断点续传 | 普通服务单次 PUT；Nextcloud 专用分块顺序上传且未持久化恢复会话 | 传输中断后，普通大文件需整文件重传；Nextcloud 也不能跨次直接恢复已成功分块。 |

## 本地复现证据

运行项目根目录下 `node docs/diagnostics/webdav-performance-probe.cjs`（Node 22.13+）。探针调用当前源码的方法，用模拟 SDK 边界隔离网络，不连接真实服务器，也不是完整 HTTP 或 Obsidian 集成测试。

- 20 个同级目录：第一个目录延迟 200 ms，其余 10 ms。共 21 次列表调用、峰值并发 10；一次运行第二批约 212 ms 才开始，总耗时约 223 ms。时间会随机器调度变化；证据是第二批必须等待第一批最慢请求。
- 列表请求模拟 HTTP 503：调用次数 1，直接失败，没有重试。
- 100 个 4 字节文件普通上传：100 次 PUT、100 次 stat，共 200 次 SDK 网络操作；不包含初始化、扫描、鉴权额外往返和同步记录写入。

这些结果证明调度、请求开销及容错缺口，不能用模拟时间推算用户真实耗时，不能据此认定昨天遭遇了 HTTP 503。

## 其他网盘的独立问题

百度、夸克、阿里适配器有整操作串行队列，直接提高引擎并发无法提升其吞吐；需要先处理同路径互斥、父目录创建、登录刷新竞争，再引入有限并发。阿里存在重复按目录列举查找文件；夸克替换流程存在多次完整读回；原生桌面 HTTP 传输还存在禁用连接复用及固定超时等问题。这些应单独优化，不作为本次 WebDAV 现场故障的解释。

## 建议实施顺序

1. **建立实际基线和安全重试。** 扩展现有阶段 Profiler，记录扫描、计划、上传、下载、确认的耗时、次数、字节数、状态码、重试次数和失败阶段。默认不记录密码、令牌、完整 URL 或正文。对只读请求的临时网络错误、429 和选定 5xx 加有预算的指数退避及抖动，尊重 Retry-After；认证失败、权限失败和路径错误不反复重试。写入超时必须先判断远端结果和版本，不能直接盲目覆盖重试；无法确认时暂停该文件，保留错误。
2. **改为持续补位的有界扫描队列。** 保留完整清单和失败保护，去掉固定批次屏障；扫描与传输分别限流，根据实际服务能力调节并发，遇到限流降速。列表不完整或扫描失败时禁止进入危险删除流程。不得默认强开 Depth: infinity，保留坚果云截断保护。
3. **减少重复查询。** 保存并传递远端 ETag/版本元数据；使用本轮扫描快照，搭配条件请求或必要的再确认，减少下载前重复 stat。上传确认采用可验证的返回信息或有界查询；验证信息不足时继续 stat。仅对能安全识别的完整忽略目录剪枝，禁止因过滤变化而误删。
4. **改善中断后的恢复。** 对已确认成功文件继续利用现有记录；临时失败在预算内恢复，明确区分成功、失败和未执行。父子依赖、冲突和删除阶段不能在前置状态不确定时继续。大文件采用字节预算控制内存，并在支持的服务上实现可恢复的分块会话；普通 WebDAV 不承诺协议本身不支持的断点续传。
5. **再优化三家原生网盘。** 目录缓存及失效、有限并发、连接复用、刷新单飞、重复读回消除和按文件大小制定传输预算。按服务分别验证，避免一套并发参数套用全部网盘。

普通用户设置页不增加并发、重试、超时等技术选项；自动策略配合简洁的进度、失败阶段和可导出的诊断摘要。

## 验收方式

同一个 WebDAV 服务和同一批文件，对照优化前后的首次同步、无变化同步、少量修改同步；分别统计总耗时、扫描耗时、请求数、实际传输字节和内存峰值。数据集覆盖大量小文件、深目录、长路径和大附件。注入临时 503、429、传输中断、写入成功但响应丢失，验证有界恢复、不会重复覆盖新版本、不会误删、不把未确认文件记为成功。未完成这些对照前不承诺具体提速倍数。

仍需现场确认：WebDAV 服务名称、文件数量与大小分布、失败原文及阶段；据此判断服务端限流、代理超时、路径限制或实际网络中断是否参与昨天的问题。
